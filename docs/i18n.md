# Translating Project Kestrel (i18n)

Kestrel's interface can be shown in several languages, and species names can
be shown in a language of their own. Both are **display only**: everything
Kestrel writes (the `.kestrel/` CSV and scene JSON, XMP sidecars, the
smart-search index) keeps canonical English names, so switching language never
changes your data and files stay readable by any build.

| Layer | Setting | Data | Code |
|---|---|---|---|
| Interface strings | `language` | `analyzer/i18n/<tag>.json` | `analyzer/js/i18n.js` (`t`, `tHtml`, `tRich`) |
| Bird names | `bird_name_language` | `analyzer/models/birds/bird_names.<tag>.json` | `trSpecies()`; `Api.get_bird_name_translations` |

## Adding or changing a string

1. Pick a key `<area>.<camelCasePurpose>` (e.g. `settings.showScientificNames.label`;
   shared buttons live under `common.*`) and add the English text to
   `analyzer/i18n/en.json`. English is the source of truth.
2. Use it:
   * **Static HTML:** `<span data-i18n="key">English fallback</span>`. Attributes
     have their own markers: `data-i18n-title`, `data-i18n-aria` (aria-label),
     `data-i18n-placeholder`, `data-i18n-alt`, `data-i18n-data-tip`. Keep the
     English text in the HTML too; it is what shows before dictionaries load.
   * **JavaScript:** `el.textContent = t('key', { name })`. Call `t()` when you
     render, not when the module loads (dictionaries arrive later). Panels that
     cache rendered text listen for `kestrel:language-changed` and repaint.
3. Add the key to every other `analyzer/i18n/<tag>.json`. If you cannot
   translate it, copy the English text; the language's `_meta.reviewed` flag
   stays `false` until a native speaker checks it.
4. Run `pytest analyzer/tests/unit/test_ui_i18n.py`.

Text that is deliberately never translated (brand names, editor product
names, file names) gets `translate="no"` so the lint ignores it.

## The escaping rule

Translations come from outside contributors and machine translation, so they
are treated as **untrusted text**. A translation must never be able to inject
markup or script.

* `t(key, vars)` returns **plain text**. Use it with `textContent`, `title`,
  `setAttribute`, `showToast`, `confirm`. Never assign it to `innerHTML`.
* `tHtml(key, vars)` returns the same text **HTML-escaped**, for the rare
  template literal that is assigned to `innerHTML`:
  ``btn.innerHTML = `<i>✨</i> ${tHtml('folderActions.upgradeButton')}`;``
  Species labels in HTML templates need `escapeHtml(trSpecies(name))` too.
* Strings that genuinely need inline formatting use the **rich** path:
  `data-i18n-rich="key"` in HTML, or `tRich(element, key, vars)` in JS. Only
  `<b> <strong> <em> <i> <code> <br>` with **no attributes** become elements;
  they are built with `createElement`, never parsed as HTML. Anything else
  (`<a href>`, `<img onerror>`, `<span class>`) is shown as literal text.
* Links, ids and styled spans stay in the HTML as **slots**. The translation
  names a placeholder and the element is moved into place, so ids, listeners
  and `href`s are never in a translation and translators can reorder freely:

  ```html
  <p data-i18n-rich="donate.footnote">Project Kestrel is free &amp; open-source.
    Every <a href="https://…" data-i18n-slot="link" data-i18n="donate.footnoteLink">contribution</a>
    helps keep it growing.</p>
  ```
  ```json
  "donate.footnote": "Project Kestrel is free & open-source. Every {link} helps keep it growing.",
  "donate.footnoteLink": "contribution"
  ```

  Values passed in `vars` to `tRich` are inserted as text nodes, never parsed.

There is no raw-HTML translation path (`data-i18n-html` was removed), and
`tools/i18n_lint.py` fails the tests if one comes back, or if `${t(...)}` /
`${trSpecies(...)}` appears inside an HTML template literal, or if `t()` is
assigned to `innerHTML`.

## Placeholders, plurals and selects

Messages use a small ICU MessageFormat subset, formatted by `i18n.js`:

* `{name}` — replaced with `vars.name` as text.
* `{count, plural, one {# scene} other {# scenes}}` — branch chosen by
  `Intl.PluralRules` for the active language; `#` is the count formatted with
  `Intl.NumberFormat` (`1,234` / `1.234` / `1 234`). `=0 {…}` matches an exact
  number. Every plural needs an `other` branch.
* `{kind, select, full {…} crop {…} other {…}}` — branch chosen by value.

Never build a plural in code (`n === 1 ? 'scene' : 'scenes'`): languages have
up to six plural forms. Use only the categories your language has — the test
knows English/German `one other`; French/Spanish/Portuguese/Italian
`one many other`; Russian/Ukrainian/Polish `one few many other` (all four
required); Japanese/Chinese/Korean `other`. Write the whole phrase inside each
branch when grammar needs it (`{count, plural, one {Rejected # photo} other
{Rejected # photos}}`). A literal `#` inside a plural branch means the number,
so keep things like "scene #{id}" outside the plural.

Placeholder names must match English exactly; you may move them, and a
language without plural forms may replace a plural with a single `other`
branch, but you may not drop or invent arguments.

## Adding a language

1. Choose a canonical **BCP-47** tag: `language[-Script][-REGION]`, e.g. `it`,
   `pt-BR`, `zh-Hans`, `es-419`. Prefer the plain language (`it`) unless the
   regional variants really differ; lookups fall back `pt-BR` → `pt` → `en`,
   and `zh-TW`/`zh-HK` → `zh-Hant`, `zh-CN`/`zh` → `zh-Hans`.
2. Copy `en.json` to `analyzer/i18n/<tag>.json`, translate the values and add a
   `_meta` block:
   ```json
   "_meta": { "language": "it", "name_native": "Italiano",
              "machine_translated": true, "reviewed": false,
              "notes": "Machine translated from en.json. Needs native review." }
   ```
3. Add the language to `analyzer/i18n/index.json` with the same
   `machine_translated` / `reviewed` flags and `dir` (`rtl` for Arabic, Hebrew,
   Persian, Urdu…; the test checks it).
4. Run the tests. Packaged builds include all of `analyzer/i18n/`
   automatically (see the PyInstaller specs).

`<html lang>` and `dir` are set from the language actually shown, so a
right-to-left language flips the document direction. The CSS has not yet been
audited for RTL (physical `left`/`right` margins, icons); expect layout work
before shipping the first RTL language.

## Machine translation and review

Several dictionaries (`es`, `pt-BR`, `ja`, `zh-Hans`, and keys added to
`de`/`fr`/`ru` after they were contributed) were machine translated. They are
marked `"machine_translated": true, "reviewed": false`, and the Settings
language list labels them "machine translated" until they are reviewed.

To review a language, a native speaker reads every string in context (run the
app in that language and walk the main window, scene dialog, Analyze dialog,
Settings and Perch dialog), fixes the JSON, and sets `"reviewed": true` in
both the file's `_meta` and `index.json`. When English text changes, update
every language (machine translation is fine) and set `reviewed` back to
`false` for languages whose string was not re-checked.

Machine translation is a starting point, not a release gate: a language ships
when the maintainers are comfortable with its review state.

## Bird names

`tools/build_bird_names_i18n.py` builds `bird_names.<tag>.json` from the
**Multiling IOC** workbook (CC BY 3.0, credited in
`analyzer/models/birds/NOTICES.md` and the README). The maps are keyed by
**scientific name**; at runtime `bird_catalog.load_name_translations` joins
them onto the catalog's English names and aliases and walks the BCP-47
fallback chain. The workbook's IOC release must match the catalog's
(`CATALOG_IOC_VERSION` in `analyzer/kestrel_analyzer/bird_catalog.py`); the
converter refuses a mismatch. When the catalog moves to a new IOC release,
rebuild the catalog first, bump `CATALOG_IOC_VERSION`, then rerun the
converter with the matching workbook:

```bash
python tools/build_bird_names_i18n.py --xlsx "/path/to/Multiling IOC 15.1_d.xlsx"
```

Languages below 50 % coverage are skipped unless named with `--include`.

## The lint and the baseline

`tools/i18n_lint.py` (run by `test_ui_i18n.py`) has two parts:

* **Unsafe sinks** — always a failure (see the escaping rule).
* **Hard-coded English** — text nodes and `title`/`placeholder`/`aria-label`/
  `alt`/`data-tip` attributes in `visualizer.html` and `culling.html` without a
  `data-i18n*` marker, and string literals in `analyzer/js/*.js` assigned to
  `textContent`/`title`/`innerHTML`/… or passed to `showToast`/`setStatus`/
  `confirm`/`alert`. Everything that existed when the lint was introduced is
  listed in `tools/i18n_untranslated_baseline.json`. The test fails on any
  string not in the baseline, and also when a baseline entry disappears, so
  the baseline only ever shrinks. After converting strings run:

  ```bash
  python tools/i18n_lint.py --update-baseline
  ```

  `python tools/i18n_lint.py` prints the current report. The JS check is a
  heuristic (it sees string literals, not every way text reaches the DOM); a
  string built in a variable first is not caught.

## Tests

* `analyzer/tests/unit/test_ui_i18n.py` — key usage, manifest, per-language
  parity (keys, placeholders, plural categories, markup), the lint, and the
  JavaScript engine tests.
* `analyzer/tests/js/i18n_engine.test.js` — runs `i18n.js` under Node with a
  small fake DOM: escaping, the rich-text allowlist and slots, plurals,
  fallback, `<html lang/dir>`, and language-switch races. Run directly with
  `node analyzer/tests/js/i18n_engine.test.js`; the pytest wrapper skips it
  when Node is not installed.
* `analyzer/tests/unit/test_bird_name_i18n.py` — converter, loaders, bridge
  and settings for bird names.
